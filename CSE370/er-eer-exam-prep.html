Core concepts, illustrated

L1 · Database basics

Database system = Database + DBMS software

A database is a collection of related data. A DBMS is the software to define, construct, manipulate and share it. The DBMS also stores a description of the data, the catalog (metadata).

Why not plain files? File processing gives redundancy and inconsistency, hard access, isolated data, integrity and atomicity problems, concurrent-access anomalies and weak security.

Characteristics of the database approach

  • Self-describing: the catalog holds the structure.
  • Program–data independence: structure is not hard-coded in programs.
  • Data abstraction: users see a conceptual model, not storage details.
  • Multiple views of the same data.
  • Sharing & multi-user transaction processing (concurrency control).

Schema vs state

The schema is the design (intension). It rarely changes. The database state (instance, snapshot, extension) is the data at one moment and changes all the time.

Data models

  • Conceptual / high-level: close to how users think, e.g. ER.
  • Representational / implementation: e.g. relational.
  • Physical / low-level: how data is stored on disk.

Languages

DDL defines schemas, DML retrieves and updates data. Also SDL (storage) and VDL (views).

When NOT to use a DBMS

High initial cost, simple single-user apps that won't change, strict real-time needs.

L1 · Three-schema architecture

Three levels, two kinds of independence

External level: the views different user groups see.

Conceptual level: the whole database for everyone (entities, relationships, constraints), with no storage detail.

Internal level: physical storage structures and access paths.

Physical data independence: change the internal schema without changing the conceptual schema.

Logical data independence: change the conceptual schema without changing external schemas or application programs. This one is harder to achieve.

L2 · Entities and attributes

An entity is a thing with independent existence (a particular student). An entity type is the set of all entities with the same attributes (STUDENT). The collection at one moment is the entity set.

A key attribute has a value unique for every entity. Underline it. An entity type can have more than one key, and a key can be composite.

Each attribute has a value set (domain). A missing or not-applicable value is NULL.

L2 · Relationships and constraints

A relationship type links entity types. Its degree is how many entity types take part: unary (recursive), binary, ternary.

In a recursive relationship the same entity type plays two roles, so write role names on the lines (supervisor / supervisee, Host / Guest, referrer / referee).

In a ternary relationship one diamond has three lines. Your sheets label them n, k, m (e.g. Borrows: BOOKS, LIBRARY, BORROWER).

The same two entity types can share several relationships (PLAYERS–TEAMS: belong_to and captain_of).

Cardinality ratio = the maximum: 1:1, 1:N, M:N.

Participation = the minimum. Total (double line): every entity must take part, also called existence dependency. Partial (single line): some may not.

Relationship attributes: in 1:1 they can move to either entity, in 1:N only to the N-side entity, and in M:N they must stay on the relationship.

(min, max) notation

Write (min,max) on the line next to entity E. It means each E takes part in at least min and at most max relationship instances. min = 0 → partial; min ≥ 1 → total.

Placement flips! Ratio labels: the "N" sits next to EMPLOYEE in DEPARTMENT 1 : N EMPLOYEE. In (min,max), EMPLOYEE gets (1,1) because each employee is in at most one department.

Weak entity type

Has no key of its own. It is identified through an owner (identifying) entity via an identifying relationship. It always has total participation in that relationship. Its partial key (dashed underline) identifies it only within one owner.

What to notice: WORKS_FOR has StartDate. It's N:1, so StartDate could migrate to EMPLOYEE (the N side). DEPENDENT is weak: double box, double diamond, double line, dashed-underlined Dep_name.

L3 · Enhanced ER (EER)

A subclass is a subset of a superclass (an IS-A relationship: an ENGINEER is an EMPLOYEE). A subclass inherits all attributes and relationships of its superclass. It can add specific (local) attributes and its own relationships.

Specialization is top-down: split a superclass into subclasses. Generalization is bottom-up: combine CAR and TRUCK into VEHICLE.

Membership can be predicate-defined (a condition on an attribute, e.g. JobType = 'Engineer'), attribute-defined (all subclasses use the same defining attribute, written on the line) or user-defined.

Two independent constraints

MeaningSymbol
Disjointat most one subclasscircle with d
Overlappingcan be in severalcircle with o
Totalmust be in at least onedouble line superclass→circle
Partialmay be in nonesingle line

So there are four combinations: disjoint-total, disjoint-partial, overlapping-total, overlapping-partial.

Hierarchy vs lattice

In a hierarchy every subclass has one superclass (single inheritance). In a lattice a subclass can have several superclasses. Such a shared subclass (e.g. STUDENT_ASSISTANT under EMPLOYEE and STUDENT) is in the intersection. It inherits from all of its superclasses (multiple inheritance).

Union type / category

A category is a subclass of the union of different superclasses. Example: OWNER is a PERSON, a BANK or a COMPANY. Draw it as a circle with ∪. Each member belongs to at least one superclass and inherits only from the one it belongs to (selective inheritance). A category can be total or partial.

What to notice: PERSON → {EMPLOYEE, STUDENT} is overlapping and partial (o, single line). STUDENT → {GRAD, UNDERGRAD} is disjoint and total (d, double line). STUDENT_ASSISTANT is a shared subclass: no circle, a subset line from each superclass.

Design practice

All 10 questions from your Chapter 3 and Chapter 4 practice sheets, plus one bonus on categories. Draw on paper first, then reveal one step at a time and compare. Diagrams follow the sheet's own answers and use its labels (lower-case n, m, and k for the third side of a ternary).

The 5-step method (use it on every scenario)

  • Nouns with their own attributes → entity types. Find each one's key; no key of its own → weak entity.
  • Describing words → attributes. Check for composite, multivalued and derived.
  • Verbs between nouns → relationship types. Check for recursive (same type twice) and ternary.
  • "each / at most / many" → cardinality ratio. "must / every / at least one" → total participation.
  • Data that belongs to the pair (grade, hours, start date, medicines per visit) → relationship attribute. It can even be multivalued.
  • Write assumptions under the diagram, but only about cardinality or participation that the question doesn't state (the sheet's rule).
